## Candidate status and known limits

This is a release candidate, **not** `v0.1.0` or a production SLA commitment.
It continues the durable queue/active admission, idempotent runner submission,
bounded receipt verification, source/log limits and bounded worker cache work.

### Changes in this candidate

- First-start admission checks both ledger contracts before writing. A rejected
  legacy namespace cannot leave an active-only ledger that blocks every restart
  (#44). Only the replica that proves ownership of the fresh active-ledger
  creation may initialize its queue peer. Ledger loss still fails closed.
- The admission pump distinguishes a legitimate queue-to-active handoff seen
  through an old snapshot from real queue-intent drift (#51). It validates the
  exact durable grant before recovery; missing ledgers and mismatched intents
  remain blocked.
- Startup and operation timing separate admission/controller API work, Pod
  scheduling, source init, source inspection and submission. Existing per-target
  metrics measure execution/export/push. Queue latency alone is not BuildKit time.
- Candidate image smoke and promotion consume captured top-level digests, not
  mutable tags shared by releases. Python package version and public PyPI file
  hashes are checked against this run's validated artifacts.

### Required upgrade procedure

Do not roll rc.9's live Service directly into this contract. Stop submissions,
drain all active jobs and runner Pods, retain receipts and ledger backups, apply
the selected release CRD and verify status-field round trips, then select a
**fresh runner namespace** and upgrade controller, runner and worker together.
Keep worker cache/storage and registry credential contracts explicit. Never
delete either admission ledger to reset capacity. A partially initialized or
lost-ledger namespace requires reviewed manual recovery or fresh-namespace
migration, not automatic reconstruction.

Follow [release gates](../releases.md), [Service migration](../service.md) and
[admission design](../service-admission-design.md) at this tag. Helm does not
upgrade files in a chart's `crds/` directory.

### Remaining validation and capacity caveats

Issues #40–#48 and #51 track remaining acceptance evidence and known capacity
risks. Passing deterministic regressions does not close their real fault,
recovery, multi-user or long-duration acceptance requirements. Review each issue
before using this candidate for your workload.

The HK synthetic OCI baseline on commit `dce349b` completed 54/54 measured builds
plus 3 warmups. At concurrency 12 its p95/p99 were about 89.6/91.3 seconds,
queue p95/p99 63/67 seconds, and wave throughput 0.131–0.153 jobs/s; throughput
was lower than at concurrency 8 despite low sampled node usage. These are
small-sample, single-workload observations, not a certified capacity limit or
evidence that the candidate has fixed every bottleneck. Control-plane CAS/status
contention was observed; full attribution and post-release reproduction remain
open in #51. Keep admission bounded, begin at modest concurrency, and do not
increase load until stage timings and Kubernetes resource requests are reviewed.

The older six-hour bounded-cache run (2037/2037 successful builds) predates this
release set. Repeat multi-hour cache and fault/recovery/multi-user validation
against the exact **public** release artifacts after the release smoke and
controlled HK upgrade pass. Stable `v0.1.0` is deferred pending stronger
correctness, capacity and long-term stability evidence.
