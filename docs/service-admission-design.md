# Service Admission Design

The original scope of [#44](https://github.com/cofy-x/kova/issues/44) is closed; additional real fault-chain acceptance is tracked by [#59](https://github.com/cofy-x/kova/issues/59).
This document describes the current Genesis v3 two-ledger contract, including the active-inclusive queue-receipt behavior introduced in Genesis v2.
The v3 candidate additionally pins worker-pool and runner OCI identities and instruments active-grant and Pod-Create receipts.
Neither the baseline tests nor this candidate claim a live committed-loss recovery PASS.
Do not deploy this branch through an in-place rolling upgrade.

## Invariants and scope

The Service has two independent, namespaced ConfigMap ledgers. Kubernetes `resourceVersion` compare-and-swap serializes each ledger's updates across concurrent reconciles and HTTP replicas. Every capacity read uses the direct API reader, not an informer cache. Ledger corruption or a replica configured with different limits fails closed. Deleting a ledger is an out-of-contract privileged operation and may erase evidence of an in-flight Create; never use deletion as recovery.

- `kova-service-admission` bounds active jobs, per-requester active jobs, and worker slots. Its limits are recorded in the ledger. The controller commits an active grant before attempting to create a runner Pod.
- Each successful active grant also records the SHA-256 hash of its requester as a fairness cursor in the **same** active-ledger CAS. Queued jobs remain FIFO within a requester. Grant ordering prefers requesters with fewer current grants, then their oldest queued jobs, and rotates the cursor's equal-grant tier after that requester; an older backlog therefore cannot recapture the only free slot on every release. If the cursor's requester has no queued group, the least-active, oldest remaining requester starts the next ring. Waiting, failed CAS attempts, and releases do not advance the cursor. A version-1 ledger without this optional field remains readable and starts with the least-active, oldest queued requester.
- `kova-service-queue-admission` bounds *HTTP-submitted* intents globally (`maxQueuedJobs`, at most 1000) and per authenticated username (`maxQueuedJobsPerRequester`). The single CAS map holds DNS-subdomain build IDs (at most 253 bytes), SHA-256 requester/request digests, random intent nonces, and creation times. The Genesis v2 schema additionally pins the exact queue receipt UID/digest and a typed cleanup disposition. In this candidate the quota remains charged through active execution until terminal receipt cleanup, so `maxQueuedJobs` bounds outstanding HTTP builds, not just waiting builds. A separate 768 KiB serialized-state guard is below Kubernetes' 1 MiB ConfigMap limit. Conflicts receive bounded backoff; exhausted contention returns retryable HTTP 429 rather than spinning indefinitely.
- Every Service replica verifies both ledgers **before** opening its HTTP listener. The legacy first-start path preflights both contracts and an empty runner namespace, then creates the active ledger first and queue ledger second; a partial pair fails closed and is never inferred from an empty List. The fresh Genesis v2 path instead requires an externally pinned runner Namespace, distinct recovery-receipt Namespace, immutable installation receipt, and `Initializing` Genesis. Its guarded bootstrap can complete either missing canonical empty ledger after a crash while still `Initializing`, pins both exact UIDs, and atomically commits Genesis; after `Committed`, a missing or replaced original ledger never gets recreated. A direct/admin CR created after readiness does not block later HTTP submissions.
- `/readyz` directly checks the CRD API and both ledger schemas and replica limits without mutation. HTTP Create checks active-ledger health before queue reservation; reservation itself validates the queue ledger and never recreates it. Reconciliation and cleanup also never recreate a missing active ledger. A missing or corrupt ledger produces retryable 503 and no newly accepted build. Existing build reads remain available. Readiness does not turn privileged ledger deletion into a supported recovery operation; protect ConfigMap writes/deletes and preserve evidence for operator review.
- Direct or administrator-created `KovaBuild` objects are **outside the HTTP queue quota**, including the global queued limit. They still need an active-ledger grant before runner Pod creation and are included in active/fair-share scheduling. No webhook currently prevents a privileged actor from bypassing the HTTP queue.

The current two-ledger schema supports `maxActiveJobs` 1–128, `workerSlots` 1–65535, and `maxQueuedJobs` 1–1000; each per-requester limit must be positive and no greater than its global limit. The active ledger has its own 768 KiB JSON-data guard. An active UID key is at most 256 UTF-8 bytes, build name at most 253 DNS bytes, requester at most 253 Unicode code points, and each grant has at most one unresolved 32-character lowercase hex Pod nonce. Queue digests, hashes and nonces must be exact lowercase hex. Both ledgers reject extra ConfigMap data keys, unknown/duplicate JSON fields, invalid identities and unsupported encoded state on read and before write; legal older version-1 optional-field omissions remain readable. A missing active ledger now blocks terminal/deletion capacity release and finalizer cleanup instead of treating unknown capacity as free.

At the full supported counts, conservative JSON bounds for the current Genesis v3 contract (active and queue state schema 2) are `8192 + 6000 × maxActiveJobs` bytes for active state and `4096 + 736 × maxQueuedJobs` bytes for queue state.
The active entry reserve includes grant and Pod receipt UID/digest links, the observed grant resourceVersion, permanent Pod attempt nonce and template digest, and cleanup markers; the queue bound includes receipt UID/digest and cleanup disposition in every entry.
At 128 active grants the bound is 776192 bytes, leaving at least 10240 bytes below the active guard; at 1000 schema-2 queue intents the bound is 740096 bytes, leaving at least 46336 bytes below the queue guard.
The earlier v1 queue bound was `4096 + 512 × maxQueuedJobs`; do not use it to size a schema-2 ledger.
Deterministic maximal-identity fixtures use Go's actual JSON encoder to exercise both state schema versions.
The active fence value may wrap from `MaxUint64` to zero: the Kubernetes `resourceVersion` CAS, not numeric ordering, fences a stale writer.
These are encoded-capacity proofs, not throughput or real-API acceptance.

An existing ledger with configuration or state outside this supported contract cannot be made valid by reducing flags while work remains. Drain old work, verify runner cleanup, stop old writers and migrate to fresh runner and recovery-receipt Namespaces with the reviewed version. The legacy partial-pair startup still fails closed. Genesis v2's [fresh bootstrap](service-genesis-recovery-proposal.md) can finish a partial canonical pair only before commitment under its exact original external identity; it does not repair a committed lost ledger.

An HTTP request CAS-reserves one queue intent before calling CR Create. Its unique nonce is stamped on the CR. In Genesis v2, that fresh owner must first create and directly qualify an immutable queue receipt in the separate pinned Namespace, then CAS-pin its exact UID/digest in the queue entry and directly confirm the pin; only then may it issue the sole CR Create. An unknown receipt or pin outcome holds the queue slot and issues no CR Create. A concurrent same-key request compares the immutable request digest, then returns a qualified existing CR or `503 queue_admission_pending`; it never issues another receipt or CR Create while the intent is unresolved. A definitive non-persisted CR Create rejection records a typed rejected cleanup disposition, UID-deletes the receipt, and releases the intent only after direct confirmation; a timeout or server/transport error does not. The response and Go/Python SDK error expose `X-Kova-Build-ID`; `GET /v1/builds/{id}` returns the same pending error while the caller's intent exists without a CR. A missing CR, elapsed time, or process restart does not prove an API Create cannot still arrive.

The controller verifies the CR's nonce, requester, immutable request digest, and—under Genesis v2—the original queue receipt link before its first active grant. The legacy baseline commits an active grant **before** removing the matching queued intent, then completes that early queue release before Pod Create. Genesis v2 deliberately skips the early release: active HTTP work occupies both ledgers until exact terminal/deletion cleanup confirms runner Pod closure, records a typed terminal disposition, UID-deletes and directly checks the queue receipt, marks the exact CR settled, then releases the queue entry. Queued CRs that fail before active admission take the same terminal path. If ledger and CR disagree, the build receives `AdmissionRecoveryRequired=True` with reason `QueueIntentDrift`; no Pod is created.

Before every Pod Create, the controller CAS-appends one in-flight nonce to its active grant and stamps that nonce on the Pod. A replacement leader cannot release the grant while the old Create might still reach the API server. A direct read observing the exact nonce resolves a lost ledger-Update response. Only a definitive Create success/AlreadyExists/non-persisted rejection or observation of a matching persisted Pod removes the marker. A retry first inspects an existing Pod and does not issue another Create while a prior nonce remains unresolved. Terminal/deletion cleanup retains the active grant until the Pod is confirmed gone and no in-flight nonce remains. An unresolved attempt sets `AdmissionRecoveryRequired=True` and public `recovery_required=true`.

Terminal, deletion, and cancellation cleanup first CAS-increments a serialized active-ledger fence, even if no grant exists, and marks an existing grant `closing`. A paused pre-fence admission CAS must conflict and re-read the current CR; a new Pod Create nonce cannot enter a closing grant. Cleanup then checks for in-flight nonces and directly re-reads the Pod before CAS-removing charged capacity. The fence counter is bounded storage, unlike permanent per-build tombstones. A definitive non-persisted Pod Create rejection clears its exact nonce; a timeout or server error does not.

## Recovery and limits of proof

These are safety-preserving reservations, not time leases. An intent or Pod nonce may remain held after a process crash. Its ledger entry records identity and time for an operator; the Service API reports pending CR creation or build recovery where a build exists. The legacy baseline releases a matching persisted CR's queue intent after the verified active handoff. Genesis v2 instead retains the queue charge until the exact terminal CR/runner cleanup and receipt disposition complete; an uncertain receipt, pin, CR Create, or deletion is not a release signal. Release an uncertain Pod nonce only after the exact nonce is observed on its Pod or the original Pod Create has a definitive non-persisted result. Audit evidence must identify the exact nonce/request; absence from a List, a deadline, a terminated process, or a leader-lease expiration is insufficient. If evidence is unavailable, retain the reservation and escalate rather than silently reclaiming capacity. There is no automatic orphan-intent scavenger or destructive recovery endpoint.

The HTTP queued limits do not count direct CR writers, do not span multiple runner namespaces, and assume all Service replicas share one runner Namespace and identical configured caps. Genesis v2 also requires the same separately pinned recovery-receipt Namespace on every replica. Both ledgers reject changed capacity settings; a limit change needs drained, fresh Namespaces and an explicit migration rather than changing one replica in place. The active limits apply to direct CRs too. A privileged actor that edits/deletes either ledger, receipt, or CR linkage can break the HTTP quota contract; protect those permissions. The legacy first-start path requires neither ledger to exist and no pre-existing KovaBuild. Genesis v2 starts only from externally provisioned fresh identities and never recreates a missing ledger after commitment. An existing queue ledger with a missing committed active ledger blocks startup even when the runner Namespace currently appears empty: an unknown in-flight Pod Create nonce cannot be reconstructed from a List. Fresh runner and recovery-receipt Namespaces are required for a new v2 epoch, not an in-place mixed-version rollout.

Deterministic tests cover two concurrent Service replicas with stale cached Lists, same-requester and global queue bursts, idempotency while full, CAS conflicts/lost responses, unknown persisted and unpersisted CR Create, leader restart, active/queue release failure, late Pod Create, terminal/deletion cleanup, limit/configuration drift, and read-only readiness faults.
Sequential single-slot grants test requester rotation across reconciler replacement; other cursor tests cover requester departure/arrival, cancelled/deleting queue heads, CAS conflict, and legacy-ledger compatibility.
Reconcile still uses a direct namespace-wide `KovaBuild` List to preserve fair queue ordering and to detect unreserved runners; the measured high-contention profile must precede any indexed or cached scheduling optimization.
A newly accepted build persists `Queued/WaitingForCapacity` once, then stops its own fixed capacity polling.
A leader-elected admission pump watches the named active ledger and queued-build lifecycle changes, chooses one candidate using the same durable fairness cursor, and wakes only that build; the build still performs the original direct-read and CAS grant.
A leader-only audit starts immediately on election, checks at most 32 active grants per pass with a rotating cursor, and continues every four seconds until its initial active set has been inspected; subsequent audits start every 30 seconds.
It wakes only unfinished or closing grants and selects the next fair candidate after startup or a missed watch event.
The default 20 active-job limit fits one pass; at the supported maximum of 128 active jobs, a stable sweep takes at most four bounded passes and roughly 16 seconds of scheduled continuation before API latency or throttling, not a 30-second wait per batch.
At full capacity, ordinary pump events read only the active ledger and skip queue-ledger decoding and full CR/Pod Lists; a possible grant validates the queue ledger and performs the original orphan check.
HTTP admission and `/readyz` independently check both ledgers even while active capacity is full.
A missing, corrupt, or mismatched ledger and a drifted queue head block new grants rather than being recreated or skipped.
In the legacy baseline, an old pump snapshot may select a still-Queued build just after another reconcile
committed its active grant and released its queue intent. Before declaring drift,
the pump performs one bounded direct reread of the active ledger, current CR and
queue. Only the exact live nonclosing UID/name/requester grant, legal allocation,
validated limits and genuinely absent intent prove this handoff. It wakes that
grant holder and retries selection from fresh state after 100 ms; it never grants
around a changed intent or missing ledger, advances the cursor, or repeats Lists
in a loop. A legal handoff is not an error-rate-limiter retry. In Genesis v2, the queue intent remains charged through active work, so an absent queue intent is not the normal early-handoff signal.
Real-apiserver E2E, high-contention performance, and the migration drill remain required before claiming a deployed strict production quota.

The pump removes the old steady-state per-build `5s` capacity loop; it does not remove the O(N) first CR Create/status transition, the serialized whole-queue ConfigMap CAS per HTTP submission, or the direct namespace-wide List when a slot opens.
The shared Service-Pod Kubernetes client rate limiter is a bounded safety budget, not a fairness scheduler: initial submissions, active/cancel cleanup, and controller reads can still contend for it.
Keep separate measurements of POST latency, queued-to-grant latency, phase-specific reconcile p95/p99, client-side throttle wait, API verb/resource QPS, and cleanup delay.
Do not infer a high-concurrency service SLA from a successful synthetic Kind queue alone.

### Historical #44 dedicated Kind fixture — not current Genesis acceptance

The current candidate requires Genesis v3, active schema 2, a pinned worker pool identity and runner manifest, and all three pre-effect receipts.
The v2 active-inclusive HTTP queue accounting described here remains in v3; earlier queue-only or waiting-only acceptance does not qualify the expanded execution and cleanup protocol.

The commands and assertions below describe the older waiting-only queue fixture. Its one active plus two waiting jobs assumed `maxQueuedJobsPerRequester=2`; Genesis v2 counts the active HTTP build too. Do **not** run these commands unchanged against a v2 installation or interpret their old PASS as v2 acceptance. A separate v2 fixture must use the external two-Namespace Genesis installer, verify queue receipts, and update all active-inclusive quota and cleanup assertions; that live adaptation is not part of this queue-only slice.

`make e2e-service-admission` is read-only by default. It accepts **only** an existing Kind context named `kind-kova-admission-*`, verifies exactly two same-image ready Service Pods, the exact active/queue limits, empty ledgers and CR namespace, static authentication, and a `never=true` runner node selector unmatched by any node. It does not create a cluster or change Helm values. An operator may prepare a fresh dedicated cluster with `KEEP_KIND_CLUSTER=true QUICKSTART_KIND_CLUSTER=kova-admission-44 SERVICE_REPLICAS=2 SERVICE_MAX_ACTIVE_JOBS=1 SERVICE_MAX_ACTIVE_JOBS_PER_REQUESTER=1 SERVICE_MAX_QUEUED_JOBS=3 SERVICE_MAX_QUEUED_JOBS_PER_REQUESTER=2 SERVICE_WORKER_SLOTS=1 make e2e-helm-quickstart`; after its CRs expire, set `serviceDaemon.runnerNodeSelector.never=true` with `helm upgrade --reuse-values` on that **same-version dedicated Kind release**. Never change ledger limits in place.

Run `make e2e-service-admission KIND_CLUSTER=kova-admission-44 KIND_KUBECONFIG=.kind/kova-admission-44.kubeconfig` for the read-only check. Then run `ADMISSION_E2E_MODE=run SERVICE_AUTH_TOKEN=service-e2e-token make e2e-service-admission KIND_CLUSTER=kova-admission-44 KIND_KUBECONFIG=.kind/kova-admission-44.kubeconfig` to exercise the two Pods directly through separate port-forwards. The script uses a fresh source URI and idempotency keys, one unschedulable blocker, 40 concurrent distinct requests, full-queue idempotent replay, and exact-name deletion of its three accepted CRs. On failure it preserves response/ID evidence and does **not** blindly clean unknown outcomes or any ledger. This one-principal live path checks the per-requester queue cap and shared active cap; independent multi-principal global-cap behavior remains covered by deterministic tests and needs a separate live scenario before #44 can close.

For leader-handoff acceptance, first ensure the dedicated cluster is empty again and run `make e2e-service-admission-failover KIND_CLUSTER=kova-admission-44 KIND_KUBECONFIG=.kind/kova-admission-44.kubeconfig` for the read-only check. Then run `ADMISSION_E2E_MODE=run SERVICE_AUTH_TOKEN=service-e2e-token make e2e-service-admission-failover KIND_CLUSTER=kova-admission-44 KIND_KUBECONFIG=.kind/kova-admission-44.kubeconfig`. It verifies the current Lease holder is one of the two ready Service Pods and belongs to the exact Service Deployment, creates one unschedulable active blocker, deletes **only that leader Pod**, waits for a different Lease holder and two same-image ready Pods, then submits a challenger. A pass requires the replacement leader to reconcile the challenger to `WaitingForCapacity` specifically because the global active job slot is occupied, while the original runner Pod UID/nonce and one active grant remain unchanged. It deletes the queued challenger before the blocker, checks both ledgers and runner Pods are empty, and retains run-scoped JSON/HTTP receipts even on success. If any write has an unknown result or a check fails, it preserves the receipts and leaves CRs for evidence-based manual recovery; it never deletes a ledger or a cluster.

The separate, explicit `ADMISSION_FAILOVER_PROMOTION=true` fixture on the sole `kova-admission-pump` Kind extends that stable handoff by UID-deleting the blocker first, then requiring the challenger's exact CR UID to become the sole `Starting` active grant and sole unscheduled `Pending` runner before UID-deleting the challenger. It keeps the default #44 path unchanged and uses `DeleteOptions.preconditions.uid` for the opt-in leader Pod and CR writes. A test-only Secret, exact Deployment/Lease/ledger/Pod identities, two-hour blocker wait, and bounded promotion/cleanup deadlines gate this live path; any ambiguity retains receipts and objects. The [testing guide](testing.md#admission-handoff-and-capacity-release-fixture) documents the full opt-in contract. Eventual promotion alone cannot attribute the wake to a ConfigMap watch because the admission pump also has a periodic audit fallback.

## Mandatory upgrade barrier

Old binaries do not honor either queue intents or Pod Create nonces. Stop new submissions; let all old active and queued builds reach a documented terminal/deleted state; verify every old runner Pod is gone; then stop **every** old controller and HTTP Service instance. Do not allow an old leader to overlap the new process. Apply the updated CRD before starting the new Service. Start the Genesis v2 candidate only with a **new runner Namespace and distinct new recovery-receipt Namespace**, an externally pinned installation receipt, fresh ledgers, and identical limits on all replicas; validate the new route before resuming submissions. This namespace boundary confines late old Pod requests to the old runner Namespace and keeps recovery receipts out of runner/controller ConfigMap permissions. Do not delete a live ledger, copy in-flight CRs into the new Namespace, or use an in-place rolling upgrade as a shortcut. If the old workload cannot drain, keep it isolated and have callers resubmit their immutable inputs under the new contract when safe.
